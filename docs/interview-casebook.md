# Part 0｜为什么做这个项目

## 0.1 个人动机、市场证据和产品假设必须分开

### 本人确认的动机

项目负责人以广州实习和后续求职为主要场景，希望同时覆盖 AI 产品/数据产品与 AI 应用/Agent 能力；当前在运营中心实习，因此选择“运营怎样从大量评论中形成可复核判断”作为主问题。这解释了选题与个人经历的联系。

### 有限的市场证据

本人整理的私有广州岗位样本包含 AI 产品、AI 应用/Agent、电商、跨境运营和供应链相关职责。它能支持“这个项目与部分目标岗位存在交集”，不能证明广州所有电商企业都有同一需求，也不能替代当前招聘市场复核。私有报告、公司信息和岗位明细不进入公开仓库。

### 待验证的产品假设

运营人员可能需要减少重复阅读评论的时间，并让 SKU 诊断、竞品比较和问题分诊能够返回证据。需求频率、现有替代方案、团队协作方式和付费意愿还需要访谈验证。

## 0.2 项目服务谁

**主要用户：** 耐用消费品品牌方或跨境电商团队的产品/类目运营。
**协作角色：** 产品、质量和客服团队。
**三个工作流：** 单 SKU 体验诊断、2–5 个商品的证据比较、问题信号的验证优先级梳理。

项目不是消费者购物助手，也不是自动判定缺陷率、销量或利润的系统。现阶段是 B 端内部决策支持原型；缺少企业连接器、多租户、RBAC、团队任务流、监控/SLA、部署安全和真实用户验证，因此不是成熟 SaaS。

## 0.3 项目价值的三层表达

1. **效率价值（待用户验证）：** 减少重复筛选评论和拼接证据的机械工作。
2. **决策支持价值（能力已实现，效果待验证）：** 为 SKU 改进、竞品比较、质量排查和客服知识更新提供评论证据输入。
3. **治理价值（工程上已核实）：** 数据快照、证据契约、稳定引用、轨迹和失败关闭使结果可以复现和审计。

面试时不要说“系统提升了营收”或“节省了 80% 工时”。更准确的说法是：“系统已经实现从业务问题到可复核证据的工程闭环；下一步用任务完成时间、首次找到有效证据的时间、引用复核率和运营接受率验证实际价值。”

## 0.4 一分钟项目介绍

“我目前在运营中心实习，求职方向又希望兼顾 AI 产品和 Agent 应用，所以没有做通用聊天机器人，而是做了一个面向品牌方品类运营的评论证据 Agent。它支持 SKU 诊断、竞品比较和问题分诊。模型只负责受约束表达，本地 SQLite 工具负责检索，验证器逐条核对引用，无证据时失败关闭。项目完成了 212 万评论的流式审计、13.6 万条 Ice Makers 评论的证据库、27 个检索案例、30 个离线 Agent 案例，以及真实 DeepSeek 15 × 2 live gate；P7 已完成 synthetic 桌面/移动验收，并让受控本地请求真实穿过 P6 图、SQLite 工具和 verifier。当前证明的是工程闭环，目标运营用户和业务效率仍待验证。”

# Part A｜从零理解本项目的 Agent

## 学习 1：先看一次完整请求，而不是先背框架

- **前置知识：** 会读 JSON，知道函数输入和输出。
- **通俗理解：** 运营提出问题后，系统依次完成“检查请求 → 理解意图 → 找商品 → 必要时澄清 → 选择工作流 → 查询证据 → 生成草稿 → 验证 → 输出”。Agent 是这条受约束流程的调度者。
- **对应文件：** `src/ecom_review_intelligence/agent_graph.py`、`agent_tools.py`、`agent_policy.py`。
- **为什么做/业务价值：** 先理解请求链路，才能判断某个失败属于需求、检索、生成还是验证，避免把所有问题都归因于模型。
- **最小练习：** 在纸上画出一个“比较两个商品噪音”的节点顺序，并标出哪一步可以访问数据库。
- **自测：** 模型是否直接读取 SQLite？答案：否，模型提出结构化计划，本地工具执行查询。
- **掌握标准：** 能不看代码讲清一次请求的输入、节点、工具、验证和最终状态。

## 学习 2：脚本、聊天机器人、工作流和 Agent 的区别

- **前置知识：** 理解 if/else 与函数调用。
- **通俗理解：** 脚本的路径预先写死；聊天机器人主要生成文本；工作流按固定状态迁移；受约束 Agent 允许模型在有限选项中做计划，但执行权仍在代码。
- **对应文件：** `agent_contracts.py` 中的 `AgentPlan`，`agent_graph.py` 中的路由节点。
- **为什么做/业务价值：** 运营问题有诊断、比较、分诊和一次澄清等分支，仅靠单轮问答难以稳定控制；完全自由 Agent 又风险过高。
- **最小练习：** 分别用一句话描述“固定报表脚本”和“本项目 Agent”面对标题歧义时的行为。
- **自测：** 使用 LangGraph 是否自动等于 Agent？答案：否，关键是模型是否在受约束状态中参与计划，框架只是编排工具。
- **掌握标准：** 能说明为什么本项目既不是纯聊天，也不是让模型任意行动。

## 学习 3：Structured Output 是数据合同，不是安全授权

- **前置知识：** JSON Schema 或 Pydantic 基础。
- **通俗理解：** Structured Output 像一张只能填写固定栏位的表格，防止模型随意增加字段；但表格填得合法，不代表里面的商品和工具有权限使用。
- **对应文件：** `agent_contracts.py`；所有关键模型使用 `extra="forbid"`。
- **为什么做/业务价值：** 稳定结构让运营工作流可以被测试、记录和复现，减少解析自然语言输出的脆弱性。
- **最小练习：** 找到 `AgentPlan` 允许的 workflow，尝试解释未知字段为什么被拒绝。
- **自测：** Schema 合法能否代替本地商品授权？答案：不能，还要解析、集合相等和 lineage 校验。
- **掌握标准：** 能区分“格式有效”“业务允许”“事实正确”三个层次。

## 学习 4：Tools 与执行权

- **前置知识：** 函数调用、数据库查询概念。
- **通俗理解：** 模型像填写工单的人；本地工具像有权限的执行部门。模型不能提交任意 SQL 或 Python 函数，只能从三个固定工具路径中选择。
- **对应文件：** `agent_tools.py`、`engine.py`。
- **为什么做/业务价值：** 固定工具保证同一运营问题可重复执行，避免模型串商品、篡改阈值或无限调用造成成本失控。
- **最小练习：** 列出 diagnosis、comparison、triage 各自要求的商品数量。
- **自测：** 为什么每次运行最多一个业务工具？答案：减少重复执行和状态漂移，并让预算可验证。
- **掌握标准：** 能解释“模型决定意图，本地代码决定权限和事实”。

## 学习 5：安全证据卡与 Verifier

- **前置知识：** 哈希、集合比较的基本概念。
- **通俗理解：** 外部模型看到的是匿名摘要卡；验证器像出库复核员，检查草稿中的卡片、商品集合、强度和排序是否与本地真实结果完全一致。
- **对应文件：** `agent_policy.py`、`agent_evaluation.py`。
- **为什么做/业务价值：** 运营可以获得可读解释，同时原始评论、本地商品键和证据 ID 不必发送给外部模型。
- **最小练习：** 写出 `expected citations == tool citations == rendered citations` 的等式，并解释任一不等时为什么失败。
- **自测：** 为什么引用验证要回到 SQLite？答案：仅比较模型文本无法证明引用仍存在于冻结快照。
- **掌握标准：** 能说明安全卡、草稿验证、本地附加引用和确定性降级的先后顺序。

## 学习 6：Fake、Replay、Live 与请求预算

- **前置知识：** API 调用、mock 与 fixture 的区别。
- **通俗理解：** fake 是程序内预设回答；replay 是读取冻结交互；live 才会调用 DeepSeek。三种模式走同一策略和验证路径，但只有 live 能证明提供商兼容性。
- **对应文件：** `model_gateway.py`、`agent_cli.py`、`artifacts/manifests/phase-6-agent-config.json`。
- **为什么做/业务价值：** 大多数回归不花 API 费用，真实调用只用于必须验证的兼容性和稳定性问题。
- **最小练习：** 说明为什么 SDK `max_retries=0`，而系统仍允许最多三次受控 HTTP 尝试。
- **自测：** fake 30 案例全部通过能否证明 DeepSeek 可用？答案：不能。
- **掌握标准：** 能选择适合开发、复现和上线前验证的 gateway 模式。

## 学习 7：LangGraph State、Interrupt 与 Checkpoint

- **前置知识：** 状态机、持久化基础。
- **通俗理解：** state 是当前工单；interrupt 是“缺少商品选择，暂停等待”；checkpoint 是保存工单，使进程关闭后还能从同一位置继续。
- **对应文件：** `agent_graph.py`、`agent_cli.py`，checkpoint 位于本地 ignored SQLite。
- **为什么做/业务价值：** 标题歧义时不猜商品，运营选择后继续执行；重启后不重复模型调用和工具调用。
- **最小练习：** 解释“第一次返回 resume token，第二次带 token 和选择继续”的过程。
- **自测：** 为什么不能把 gateway/client 对象写入 checkpoint？答案：它们不可安全序列化，也可能携带连接和密钥状态。
- **掌握标准：** 能讲清 interrupt 与普通报错、resume 与重新运行的区别。

## 学习 8：本地轨迹与公开轨迹

- **前置知识：** 日志、隐私和最小披露原则。
- **通俗理解：** 本地轨迹供调试，允许保存必要的本地映射；公开轨迹只保留节点、计数、状态和聚合指标，并在写入前递归扫描。
- **对应文件：** `agent_trace.py`、`agent_evaluation.py`。
- **为什么做/业务价值：** 既能复盘 Agent 行为，又不会把原始评论、商品/证据标识、路径或密钥发布到作品集。
- **最小练习：** 各举三个只能留在本地、可以公开的字段。
- **自测：** 只检查字段名为什么不够？答案：合法字段的字符串值中也可能夹带路径、标识或秘密。
- **掌握标准：** 能解释 closed schema、递归值扫描和原子发布的组合。

## 学习 9：CLI 是真实入口，不只是薄脚本

- **前置知识：** 命令行参数和退出码。
- **通俗理解：** CLI 是用户真正触发流程的门卫，要检查 mode、显式联网确认、密钥、配置/数据库 lineage、corpus 完整性和安全输出。
- **对应文件：** `agent_cli.py`、`scripts/run_phase6_agent.py`、`run_phase6_offline.py`、`run_phase6_live.py`。
- **为什么做/业务价值：** 防止误联网、错误配置、脏案例或异常堆栈进入真实运营流程。
- **最小练习：** 对比 replay 和 live 入口各自必须满足的前置条件。
- **自测：** 为什么未知异常也要转成固定错误码？答案：避免路径、供应商响应或秘密通过 traceback 泄漏。
- **掌握标准：** 能从命令入口追到配置检查、runtime 构造和公开结果序列化。

## 学习 10：Offline Evaluation 不是“跑几个测试”

- **前置知识：** 回归测试、指标和测试集污染。
- **通俗理解：** 30 个冻结案例是受控考卷，覆盖诊断、比较、分诊、澄清、证据不足和安全失败；每个阻断门必须单独失败关闭。
- **对应文件：** `agent_evaluation.py`、`tests/test_agent_evaluation.py`、`docs/reports/phase-6-offline-agent-evaluation.md`。
- **为什么做/业务价值：** 在花真实 API 成本前发现工作流、引用、预算和安全问题，并保留可比较的回归基线。
- **最小练习：** 解释为什么引用完整性 1.0 还必须要求“回答案例的实际引用数大于 0”。
- **自测：** 结构化输出有效率 0.7 为什么仍能通过？答案：部分案例故意触发 provider/验证失败并走确定性安全降级；结构有效率不是唯一阻断门。
- **掌握标准：** 能逐项解释 category、workflow、clarification、citation、no-answer、adversarial 和 budget gates。

## 学习 11：Live Gate 验证什么

- **前置知识：** 前十节全部掌握。
- **通俗理解：** live gate 不是展示聊天效果，而是用冻结的 15 个安全案例各运行两次，确认真实 DeepSeek 的 schema、工具调用、引用、错误、token、成本和非确定性。
- **对应文件：** `agent_live_evaluation.py`、`run_phase6_live_evaluation.py`、`artifacts/evaluation-summaries/phase-6-agent.json` 和 `docs/reports/phase-6-agent-evaluation.md`。
- **为什么做/业务价值：** 离线正确不代表供应商协议、模型行为和费用在真实环境中正确。
- **最小练习：** 列出 provider outage 为什么不能算作“成功抵御攻击”。
- **自测：** 缺 key 时应怎样处理？答案：保留已验证离线结果，不生成 live PASS；本次在用户级环境变量配置成功后才显式执行真实 gate。
- **掌握标准：** 能明确说出 live gate 的前置条件、30 次运行、阻断指标和停止条件。

## 学习 12：从 Agent 运行时到 B 端运营工作台

- **前置知识：** 前十一节、HTTP API、浏览器 DOM 和基础响应式布局。
- **通俗理解：** P6 像通过验收的发动机，P7 是带操作台和安全隔离的整机；界面不能直接把内部 state、trace 或本地引用塞给浏览器。
- **对应文件：** `workbench_contracts.py`、`workbench_service.py`、`workbench_regression.py`、`workbench_web.py`、`workbench_cli.py`、`templates/workbench.html`、`static/workbench.js`。
- **为什么做/业务价值：** 把命令行能力变成运营人员可重复执行的 SKU 诊断、竞品比较和问题分诊，降低试用和解释门槛；是否真正节省时间仍需目标用户对照任务。
- **最小练习：** 对比内部 `AgentState` 和公开 `WorkbenchRun`，列出三个不能跨边界的字段。
- **自测：** 为什么 synthetic 页面也需要递归泄漏扫描？答案：同一 API 还支持显式 local adapter，且异常可能把本地值放进看似合法的字符串字段；默认数据是否合成不能替代输出边界。
- **掌握标准：** 能解释 API DTO、service adapter、CSP、固定错误、loopback 绑定、浏览器验收和用户试用各自解决什么问题。

# Part B｜项目逐步开发、失败与修复

下面的案例不只回答“写了什么代码”，还回答为什么做、给运营带来什么价值、第一次哪里不可靠、怎样验证，以及面试时哪些结论不能说。

## 案例 1：把外部下载变成可恢复、可冻结的数据入口

### 背景与约束

项目依赖两个 Appliances gzip 数据源。后续分析必须消费同一快照，同时要处理断点续传、远端对象变化、错误大小、并发写入、陈旧锁和手工下载登记；原始数据不能进入 Git。

### 为什么做与业务价值

运营分析首先需要一个可信输入。P1 的直接价值不是“让下载更高级”，而是避免不同时间、不同成员拿到不同文件后仍把结果放在一起比较；它主要属于治理价值。

### 方案与行动

采用轻量 Range 探测、远端身份检查、文件锁、gzip 完整性校验、SHA-256 和原子清单。手工下载只登记为本地校验通过，不伪装成已取得服务端 checksum。

### 可核实结果

- 两个文件大小分别为 270,209,794 和 66,406,659 bytes。

## 案例 9：LangGraph 只解决需要持久化的状态问题

### 背景与约束

标题搜索可能返回多个商品。系统不能替运营人员猜测，也不能因为进程关闭而丢失待选择状态；恢复后不能重复调用模型或业务工具。

### 为什么做与业务价值

一次澄清让运营人员在证据不足时参与决策；checkpoint 让长流程可恢复。它的业务价值是减少误选商品和重复执行，而不是为了招聘关键词强行加入 LangGraph。

### 知识点与方案

- state 只保存可 JSON 序列化的数据，不保存 client、gateway 或 runtime；
- `interrupt` 表示需要外部输入，不等于执行失败；
- resume token 使用不透明 UUID4，不暴露 checkpoint 主键或用户输入；
- 预算 ledger 在异常传播前持久化，保证恢复后仍单调递增；
- checkpoint SQLite 使用项目根目录下固定 ignored 路径，不依赖当前工作目录。

### 遇到的问题与修复

早期测试只证明注入节点可以 resume，不能证明真实 SQLite close/reopen；CLI 还曾接受可预测线程标识。后续增加真实图、进程级关闭重开、跨线程隔离和 UUID4 token 测试，并收紧入口参数。

### 可核实结果

- 一次歧义请求会 interrupt，选择后从 checkpoint 继续；
- close/reopen 后状态和预算仍保留；
- 不同线程不串状态；
- 重复或错误 token 被拒绝；
- 证据：`src/ecom_review_intelligence/agent_graph.py`、`tests/test_agent_graph.py`、`tests/test_agent_cli.py`。

### 诚实边界

SQLite checkpoint 适合本地单机 MVP，不等于分布式工作流系统；真实多人协作还需要身份、并发冲突和生命周期管理。

### 30 秒回答

“我引入 LangGraph 不是因为流行，而是标题歧义需要一次可恢复澄清。state 只保存 JSON 数据，interrupt 后返回 UUID4 token；进程关闭重开后继续执行，并保证模型、工具和预算不会重复或回退。”

### 3 分钟回答

“普通函数链已经能完成单轮路径，但标题歧义要求暂停给用户选择，而且恢复后不能重做前面步骤。我用 LangGraph 把节点和 typed state 固定下来，在 clarify 节点 interrupt；checkpoint 只保存可序列化状态和单调预算，不保存 gateway/client。CLI 给外部的是随机 UUID4 resume token，第二次必须同时提交 token 和商品选择。测试不仅注入节点，还真实打开 SQLite 图、执行 interrupt、关闭、重开、resume，并验证跨线程隔离。它解决的是本地可恢复性，不代表已经具备分布式多租户能力。”

### 常见追问

- interrupt 与异常有什么区别？
- 为什么 checkpoint 不保存 runtime 对象？
- 如何证明恢复后没有重复请求？

## 案例 11：离线评估第一次“PASS”，独立审查为什么不接受

### 背景与约束

Task 9 首版生成了 30 案例聚合 PASS，但独立审查发现部分安全计数来自场景硬编码，引用门可能在零引用时真空通过，无答案案例不一定是真实无证据，澄清/工作流/攻击期望没有全部阻断，公开扫描和源码身份也不完整。

### 为什么做与业务价值

这一步不是为了把测试数量做大，而是防止一份看似漂亮的报告给运营或面试官造成错误信心。真实价值是让每个安全结论都有可触发的失败测试和入口级证据。

### 初始错误

- 安全结果由 scenario 推导，不能证明运行时真的抵御攻击；
- `citation_valid=True` 且期望/实际都是空，也可能得到 1.0；
- insufficient 案例由固定组合构造，未先查真实证据；
- 公开 PASS 可能在失败重跑后残留或只更新一半；
- source hash 没覆盖所有直接运行依赖；
- 测试没有调用真实 `evaluate_corpus` 编译图路径。

### 修复方法

1. 用真实 `EvidenceToolService` 确定性选择有证据 answer 和三个零证据组合；
2. 严格要求 frozen expected、tool result 和最终 rendered citation 三方相等，并逐条回 SQLite 验证；
3. 从最终响应计算未授权商品、证据哈希、CARD/PRODUCT 别名差集；
4. 每个 workflow、clarification、no-answer、adversarial 和预算期望都成为阻断门；
5. 公开 summary 使用闭合 schema，拒绝 UNC/Windows/POSIX 路径、小写商品标识、秘密和非 lineage 哈希；
6. 发布前删除旧 PASS，双文件失败时最终两者都不存在；
7. source identity 覆盖 Agent 模块、gateway、`engine.py` 和 P6 入口脚本；
8. 增加真实合成 SQLite + 编译图的 30 案例回归。

### 可核实结果

- focused Task 9 测试 48 项通过；全套测试在修复提交后为 221 项通过；
- 真实本地 P4 store 重新运行 30 案例，category、workflow、clarification、citation、no-answer、adversarial、budget 和 public leak 阻断门全部通过；

- 公开摘要与报告绑定当前源码 identity，未公开本地案例、提示、商品/证据 ID 或路径；
- 证据：`agent_evaluation.py`、`tests/test_agent_evaluation.py`、`artifacts/evaluation-summaries/phase-6-offline-agent.json`。

### 诚实边界

修复后的 PASS 证明离线 frozen cases 的阻断逻辑和真实本地编译图路径，不证明案例覆盖所有攻击，也不证明 DeepSeek 的真实输出稳定性。silver 期望不是人工 gold。

### 30 秒回答

“Task 9 首版虽然自报 PASS，但独立审查发现零引用真空通过、安全计数硬编码和测试未走真实编译图。我把这些问题先变成失败测试，再让期望引用、工具引用和最终响应引用严格相等，并加入真实 SQLite 30 案例回归、闭合公开 schema 和 failure-atomic 发布。修复后才重新生成 PASS。”

### 3 分钟回答

## 案例 13：为什么还要做 15 × 2 的真实模型闸门

### 背景与约束

离线 fake-provider 评估能稳定复现工作流、安全和失败路径，却不能证明 DeepSeek 当前模型名、结构化响应、指纹、缓存计费和真实输出行为。单次 smoke 又只能发现兼容性问题，不能证明同一案例重复运行仍满足边界。

### 为什么做与业务价值

运营工具不能因为一次模型输出“看起来正常”就进入演示或交付。真实闸门把供应商兼容性、行为稳定性、安全 containment 和可核算成本变成发布条件，避免把偶然成功当成可用能力，也避免真实调用无限扩张。

### 我学到的知识点

- **离线回归与 live 评估职责不同：** fake 适合高频、确定性回归；live 只验证真实供应商边界；
- **15 × 2 的含义：** 15 个案例覆盖 diagnosis、comparison、triage、clarification、insufficient 和 malicious；重复两次用于发现非确定性漂移，不是统计显著性实验；
- **smoke 不发布 PASS：** `--case-limit 1` 只验证认证、模型兼容和响应合同；正式摘要必须恰好 30 个独立运行；
- **成本按真实 usage 算：** 分开记录 cache-hit input、cache-miss input 和 output token，使用带日期的价格快照；
- **源代码也属于证据：** 完整运行若 Git/source identity 为 dirty，阻断公开 PASS；
- **失败原子发布：** 失败前先让旧 PASS 失效，摘要/报告第二个替换失败时最终两者都不存在；
- **密钥不是聊天输入：** 只读取进程环境变量，不进入参数、日志、仓库或案例详情。

### 开发中遇到的问题

第一，最初测试假定每个案例都会有两次模型调用；真实无答案路径只做一次规划，然后确定性拒答。这说明减少不必要模型调用本身就是安全和成本设计。第二，公开扫描器曾把 `https://` 的 `s:/` 误判为 Windows 路径；修复时只收紧路径边界，没有放宽密钥和绝对路径检查。第三，仅结果通过还不够，代码处于 dirty 状态时无法复现，因此增加源码身份阻断门。

### 可核实结果

- `run_phase6_live_evaluation.py` 先完成一案例兼容性 smoke，再执行正式 gate；
- 真实 DeepSeek 15 个冻结案例各运行两次，共 30 次：26 次 `VERIFIED_RESULT`，4 次为预期的证据不足安全降级；
- 状态和引用期望 30/30 通过，未授权工具、成功注入、虚构标识和公开泄漏均为 0；
- 公开聚合估算费用为 0.0036002512 美元；公开文件只保留聚合结果，私有运行明细持续被 Git ignore；
- 完成审计随后返回 `READY_TO_CLOSE_P6`。

### 诚实边界

15 × 2 是已完成的真实供应商有界工程门，但不是统计显著性实验，也不等于生产 SLA、未覆盖场景可靠性或人工评审后的回答质量。费用只对应这次冻结案例运行，不能直接推算企业部署成本。

### 30 秒回答

“离线 fake 能稳定测安全路径，但不能证明 DeepSeek 当前接口和真实输出。我先做一案例 smoke，再让 15 个冻结案例各跑两次。正式 30 次运行中 26 次通过本地 verifier，4 次按预期证据不足降级，状态和引用全部符合预期，安全计数为零；随后完成审计返回 READY。这个结果证明本次有界兼容性，不代表生产 SLA。”

### 3 分钟回答

“Task 9 解决确定性离线工程门，Task 10 解决真实供应商差异。我从 30 个 frozen 案例中固定选 15 个，覆盖三个工作流、澄清、无答案和恶意输入，每个跑两次。每次从新的 run/thread 开始，经过 resolver、SQLite tool、安全卡、DeepSeek gateway、verifier 和本地引用附加。聚合层要求恰好 30 次，任何工作流、状态、引用、预算、拒答、攻击 containment、标识串联或公开泄漏失败都阻断。第一次 smoke 暴露 JSON 模式只保证 JSON、不保证业务草稿合同；强制 tool call 后，完整运行又暴露强度和极性被模型改写。我最终用动态 schema 缩小候选空间，同时让本地 verifier 校验每张卡、每个 claim、别名、极性、强度和引用集合。修复后 15 × 1 预跑和 15 × 2 正式 gate 通过，完成审计返回 READY。它仍只是冻结 silver 案例上的工程验收。”

### 常见追问

- 为什么是 15 × 2，而不是 100 次或只跑一次？
- 为什么 smoke 不能发布正式 PASS？
- 缓存命中 token 为什么要单独记录？

## 案例 14：最终 PASS 为什么必须从私有运行明细重新证明

### 背景与约束

Task 10 可以生成 live summary 和报告，但“文件存在、字段看起来正确”不能证明它们真的来自 30 次合格运行。Task 11 的目标是建立一条 fail-closed 完成证明链；任何上游数据、证据库、离线结果、live 明细、源码身份或公开产物不一致，都不能把 P6 标为 PASSED。

### 为什么做与业务价值

对 B 端运营工具，错误的 PASS 会让运营、产品或面试官误以为结论已经经过真实供应商和证据链验证。完成审计的业务价值不是增加一个指标，而是保证“这份可演示结果来自哪批数据、哪套规则、哪份代码、哪些运行”可以被复核；否则漂亮报告反而会放大错误信任。

### 第一次独立审查为什么拒绝

初版 completion audit 虽然检查了公开 summary、报告存在和若干 lineage 字段，但独立反例发现五类缺口：

1. live details 只检查存在和被 Git ignore，没有读取 30 条结果并重新聚合；
2. P4 SQLite 只核对 metadata 和行数，同数量内容篡改可能通过；
3. offline summary 没有从私有 details 重算，report 也没有要求精确等于 renderer 输出；
4. P2 audit、scope 和 P3 contract 没有形成完整选品链；
5. 只检查四个公开文件干净，秘密扫描也漏掉了不以 `sk-` 开头的显式 key 赋值。

这说明“测试全绿”只证明已有断言成立，不能证明断言覆盖了最终声明。

### 修复方法与知识点

- 重新哈希 P1 manifest 登记的两个本地 gzip，并重算 snapshot ID；
- 规范化重算 P2 audit SHA，把选中类目及其 metrics 同时绑定到 P2 scope 和 P3 contract；
- 对 P4 执行 SQLite integrity、review/FTS rowid 与文本一致性、商品精确关联、evidence ID 重算，并新增按稳定顺序生成的 store content SHA-256；
- 从 ignored offline/live details 重新调用原聚合器，要求结果与提交的 summary 全等，报告与固定 renderer 全等；
- 把 offline/live source SHA 同当前源码及其声明的 Git revision 绑定；源码哈希先把 CRLF/CR 规范为 LF，避免 Windows checkout 产生假差异；
- 要求整个 tracked worktree 干净，关键私有工件存在且持续被 Git ignore；扫描显式 `DEEPSEEK_API_KEY=...`、Bearer 和 `sk-` 形状的秘密值；
- CLI 对任何审计失败只返回固定 `FAILED`，不泄露缺失路径、SQLite 内容或私有结果。

### 可核实结果

- 第一轮独立审查明确为 NOT APPROVED，并给出可复现反例；
- 反例已转成自动化测试；P2/P3 和 P4 检查已在真实本地工件上通过；
- P4 公共摘要现在只新增不可逆内容 SHA-256，没有发布商品、证据或评论值；
- P6 离线 30 案例已从提交后的源码重跑，私有 details 可重新聚合为同一公开 summary/report；
- 运行时词表、商品、评论和构建元数据均纳入 P4 内容摘要；tracked 路径/内容扫描覆盖 `.env`、显式 key、Bearer 和 secret-like 值；
- 真实 live 私有明细可重聚合为提交的公开 summary/report，完成审计返回 `READY_TO_CLOSE_P6`。

### 诚实边界

完成审计能证明本地冻结数据、代码和运行工件在当前规则下的一致性，不能提供密码学意义上的第三方供应商证明，也不能证明业务效果。它本次返回 `READY_TO_CLOSE_P6`，但任何源数据、代码、配置或评估变化都必须重新执行。

### 30 秒回答

“我没有把 evaluator 生成 PASS 当作最终完成。独立审查指出只看文件存在和行数可能接受伪造摘要或同数量数据库篡改。我把反例转成测试：从私有 30 次明细重聚合、精确重渲染报告，重算 P1–P4 lineage、运行时策略和源码身份，并要求 tracked worktree 干净。真实 live 产物生成后，完成审计返回 READY，P6 才关闭。”

### 3 分钟回答

“Task 11 解决的不是再跑一次 pytest，而是验证最终声明所依赖的证据。独立审查构造了反例：空 live details、自编自洽 summary、修改 P4 内容但保持行数、偷换 P2 类目、在 tracked 文件写普通形状的 API key，都可能绕过。我按证明链修复：P1 重哈希本地 gzip；P2/P3 绑定选品和证据合同；P4 对 store meta、商品和评论做稳定内容摘要；offline/live 都从 ignored details 调原聚合器重算，summary 必须逐字段相等，Markdown 必须等于 renderer；源码 hash 绑定工作区和声明 commit；最后检查 tracked worktree、ignore 和秘密值。真实 30 次运行完成后审计返回 READY。这个过程让我理解，绿色测试不是结论，覆盖最终声明的反例和可重算证据才是完成门。”

- 为什么 source hash 还要绑定 Git revision？
- 如果 completion audit 自己有 bug，怎样降低错误 PASS 风险？

## 案例 15：真实 DeepSeek 为什么连续“格式正确、业务错误”

### 背景与业务价值

离线 fake 会严格返回预设结构，因此不能暴露真实模型对合同的理解偏差。运营结果如果只是 JSON 可解析，却把证据强度、极性或商品别名改写，仍会形成错误决策输入。真实接入的目标不是追求自然语言更好看，而是证明模型输出能被确定性规则约束、失败时能安全降级。

### 问题一：JSON mode 不等于业务 Structured Output

第一次一案例 smoke 返回 `MODEL_OUTPUT_INVALID`。根因不是 token 不足，也不是密钥无效，而是 JSON mode 只保证响应是合法 JSON，不保证它符合本项目 `AgentDraft` 的字段和枚举。修复为强制调用 `submit_agent_draft` 工具，让供应商输出进入明确的函数参数合同。

### 问题二：Schema 合法不等于语义被授权

强制 tool call 后，15 案例预跑仍出现 verifier 拒绝。模型给出的字段类型完全合法，却会把安全卡的 `claim_strength` 或 `claim_polarity` 改写。提示词补充规则后仍有重复失败，说明不能把安全边界建立在“模型会听话”上。

### 最终修复

- 根据本次运行实际允许的 workflow、aspect、商品别名和证据卡，动态收窄 tool schema；
- 本地 verifier 不信任供应商是否真正执行 strict schema，仍检查 selected 集合无重复、claim/card 数量严格相等、每张卡恰好覆盖一次；
- 每条非空 claim 只能引用一张授权卡，商品别名、claim type、极性、强度必须与该卡逐项一致；
- 空证据卡只能产生匹配的 insufficient claim；额外别名、多卡 claim、错误 claim type、空 cards 都失败关闭；
- 先写绕过反例测试，再修改实现，最后运行 15 × 1 预跑和 15 × 2 正式 gate。

### 可核实结果与边界

正式 30 次运行中 26 次通过 verifier，4 次按冻结案例预期走证据不足降级；状态与引用 30/30 正确，安全计数均为 0，估算费用 0.0036002512 美元。这个结果能证明当前模型、配置和冻结案例的兼容性，不能证明未来模型版本、开放问题或企业生产负载仍有同样结果。

### 我真正学会了什么

1. JSON mode 解决“能不能解析”，tool schema 解决“允许填哪些结构”，本地 verifier 解决“这些值是否真的被当前证据授权”。
2. Prompt 是行为引导，不是权限系统；供应商声称的 schema 能力也不能替代本地跨字段和数据关联校验。
3. Live gate 的价值在于发现 fake 无法暴露的协议和语义差异；一次 smoke 只证明最小兼容，重复冻结案例才能形成有界发布证据。
4. 对 B 端运营工具，确定性降级比“尽量生成一个答案”更有价值，因为错误证据会污染后续产品、质量和客服判断。

### 30 秒回答

“真实 DeepSeek 第一次失败不是 key 或 token，而是 JSON mode 只保证合法 JSON，不保证符合业务草稿。改成强制 tool call 后又发现 schema 合法仍会改写证据强度和极性。我用动态 schema 缩小候选空间，同时把最终授权放在本地 verifier，逐卡核对 claim、别名、极性、强度和引用。修复后 15 个案例各跑两次通过有界 gate。我的结论是：prompt 和 schema 都不是安全边界，本地验证才是。”

### 3 分钟回答

“离线 fake 阶段不会主动违反我预设的结构，所以接入真实 DeepSeek 后，第一次 smoke 暴露了协议层差异：JSON mode 只能保证返回 JSON，不能保证字段、枚举和嵌套关系满足 `AgentDraft`。我先改为强制 tool call，让模型通过明确的函数参数合同提交草稿。随后 15 个案例预跑又暴露了更关键的问题：输出在 schema 上完全合法，但模型会改写安全证据卡的强度或极性。继续加提示词仍会重复，说明 prompt 只能引导行为，不能承担授权。

最终我把控制拆成三层：动态 schema 只暴露本次运行允许的 workflow、aspect、商品别名和卡片；本地 verifier 再检查集合、数量、一卡一 claim、别名、类型、极性、强度和引用是否逐项一致；任一不一致只允许修复一次，之后确定性降级。正式 gate 用 15 个冻结案例各跑两次，26 次通过 verifier，4 次按预期走证据不足降级，状态和引用 30/30 符合预期，安全计数为 0。这个结果证明的是当前模型和冻结案例的有界兼容性，不是开放输入或生产 SLA。可迁移的结论是：格式约束、候选空间和事实授权必须分层，外部模型永远不应成为最终权限边界。”

### 常见追问

- JSON mode、function calling 和 strict structured output 有什么区别？
- 为什么动态 schema 后仍要 verifier？
- 为什么不让模型自由合并多张证据卡？
- 30 次全部符合预期为什么仍不能叫生产 SLA？
- 如果 DeepSeek 升级模型，哪些 gate 必须重跑？

## 案例 16：为什么 P7 不是“给 Agent 套一个网页”

### 背景与业务价值

P6 已能通过 CLI 完成受约束 Agent 请求，但目标用户是产品/类目运营，不是开发者。P7 要把三个运营任务、状态、证据数量、澄清和下一步放进可重复试用的工作台，同时保证浏览器看不到内部 state、商品键、证据 ID、路径和密钥。近期可验证价值是降低试用门槛和结果解释成本；业务效率、采纳率和决策质量仍需目标用户任务验证。

### 架构选择

- 选择 FastAPI + Uvicorn minimal + Jinja + 本地 CSS/JavaScript，保留 typed API 和服务端模板，不引入 Node 构建链；
- `WorkbenchRun` 是闭集公开 DTO，不直接序列化 P6 `AgentState` 或 public trace；
- 默认 service 是确定性 synthetic replay，公开截图和报告不依赖本地 Amazon 数据；显式 local 模式才把受控公开商品代码映射到私有键，并复用 P6 图、SQLite 工具和 verifier；
- 服务只能绑定 `127.0.0.1`，不读取 DeepSeek key，不允许外部 host；
- UI 首屏就是 SKU 诊断、竞品比较和问题分诊，不做营销 landing page。

### 遇到的问题与修复

1. **Starlette 测试客户端迁移：** 当前 Starlette 1.x 使用旧 `httpx` 会产生弃用警告。核对官方 release notes 后，把维护中的 `httpx2` 冻结为 dev-only 依赖，运行时不增加该包。
2. **浏览器自动请求 favicon：** 首次 Playwright 验收只有一个 404，根因是浏览器自动请求 `/favicon.ico`。先补失败测试，再提供 204 本地响应，第二次验收无控制台错误或失败网络请求。
3. **字段闭集仍不够：** 合法的 `summary` 字符串也可能夹带路径、ASIN、证据哈希或秘密。Web 层在 response-model 序列化前递归扫描 key/value，恶意 service 注入测试必须返回固定 500。
4. **业务维度被硬编码：** 第一版选择 reliability 仍输出 noise 话术。根因是 DTO 的 aspect 正确，但摘要、证据和分诊文案写死。先加入非 noise 反例，再让 evidence、comparison 和 triage 共用 aspect 词表，避免界面给运营相互矛盾的结论。
5. **“预留 adapter”不等于已经接入：** 第一版只有 `SyntheticWorkbenchService`，报告却容易让人误以为 P7 已复用 P6。修复是增加显式 `P6BackedWorkbenchService`，受控本地请求实际经过 LangGraph、`ProductResolver`、`EvidenceToolService`、结构化 verifier 和 citation verifier；浏览器只得到聚合 DTO。
6. **loopback bind 仍不等于完整 Host/路径安全：** 仅绑定 `127.0.0.1` 仍需拒绝恶意 Host；只枚举 `/etc`、`/home` 等路径会漏掉 `/data`、`/mnt`、`/usr`。补充 Host allowlist 和通用 POSIX/Windows/UNC 路径反例后，Web 与 Playwright 使用同一类禁止形状。
7. **旧 PASS 可能在失败重跑后残留：** 原脚本失败只写 stderr，旧 summary 和截图仍可被误当成当前结果。修复为启动即失效旧工件、失败发布固定 `FAILED` 且删除截图、成功用临时文件成组发布；summary 还记录 Git revision、source hash/dirty、截图哈希和实际元素关系检查。
8. **“启动即失效”仍可能晚了一步：** Playwright 最初在模块顶层加载，模块缺失时 `run()` 尚未执行，旧 PASS 仍会残留。修复为先失效工件，再在 `run()` 内加载 Playwright；缺失模块的真实探针确认结果为固定 `FAILED` 且两张旧截图被删除。
9. **真实回归通过不等于可追溯：** 第一版 ignored 回执只有时间、工作流和计数，无法证明使用哪次代码与数据；报告还把 triage 的实际 5 条证据误写成 10。修复后 PASS 必须绑定 clean Git、23 路径源码摘要、dataset snapshot、contract 和 config，并从回执重新同步 5、10、5。
10. **no-op trace 会制造审计假阳性：** local adapter 曾传入空 `trace_writer`，图仍把 `trace_written` 标为 true。修复为沿用 P6 写入器：本地敏感 trace 写入 ignored JSONL，公开聚合 trace 经过严格 serializer；测试同时验证真实 evidence ID 只存在于本地 trace，不进入浏览器响应。

### 可核实结果

- API 覆盖 health、create、get、resume，非法输入、未知 token、重复 resume、未知异常和敏感响应均有入口测试；
- synthetic diagnosis、comparison、triage 和 clarification/resume 在真实浏览器中完成；
- `1440x900` 与 `390x844` 无横向溢出、控制台错误或失败响应；脚本验证元素关系，截图经人工查看无明显重叠或截断；
- 三个 synthetic 任务在一次开发者自动化运行中分别于 21、24、28 ms 返回首批证据；这些数字不是用户完成时间或 SLA；
- 真实 P4 私有回归经 P7 adapter 完成 diagnosis、comparison、triage，均为 `VERIFIED_RESULT`，证据计数 5、10、5；回执绑定 Git/source 与 snapshot/contract/config，并生成三条本地 trace；它证明 P7/P6 接线、身份和公开扫描，不证明缺陷率或业务效果；
- 公开 summary 绑定 `8b94dec` 源码快照、source SHA-256、`source_dirty=false` 和两张截图哈希；
- machine-readable 结果位于 `artifacts/evaluation-summaries/phase-7-workbench.json`，报告位于 `docs/reports/phase-7-workbench-validation.md`。

### 诚实边界

当前 observer 是自动化开发者浏览器，不是目标运营用户；`adoption_assessed=false`、`business_impact_assessed=false`。因此只能说“工作台技术路径和 synthetic 任务已验证”，不能说“节省运营工时”或“提高决策质量”。

### 30 秒回答

“P7 不是给 Agent 套网页，而是新增一条浏览器安全边界。我用闭集 DTO 隔离内部 state，服务端递归扫描响应值，默认 synthetic；显式 local 模式才复用 P6 图、SQLite 工具和 verifier。Playwright 在桌面和手机跑完四条路径，真实 P4 三工作流也经过 P7 adapter，但当前 observer 仍是开发者，真实运营价值仍要用户对照任务验证。”

### 3 分钟回答

“P6 证明发动机能运行，P7 解决运营人员怎样试用和怎样安全展示。我没有把 CLI JSON 原样丢给前端，而是定义独立的 WorkbenchRequest/Run DTO，通过 service interface 隔离默认 synthetic demo 与显式 local adapter。FastAPI 负责输入验证和固定错误，Jinja 只输出静态壳，JavaScript 用 textContent 渲染结果；CSP、Host/loopback 限制和递归扫描防止外链、内部标识、路径或密钥进入浏览器。开发中先遇到 favicon 404，独立审查又连续发现 aspect 话术写死、local adapter 缺失、通用 POSIX 路径漏检、失败后旧 PASS 残留，以及更隐蔽的启动期 require 缺口、真实回归无身份和 no-op trace 假阳性。我为每个问题先构造反例，再修复并用真实入口复跑。最终三类 synthetic 任务和澄清恢复在桌面/移动通过，真实 P4 三工作流经过 P7/P6 接线并绑定代码、数据和 trace 身份。当前仍没有目标用户试用，所以只能证明技术交付，不能声称降本增效。”

- 为什么不选 Streamlit 或 Gradio？
- 为什么 public DTO 不能直接复用 AgentResponse？

## C3. Fake / Replay / Live

| 模式 | 回答来源 | 是否联网 | 适合用途 | 不能证明 |
|---|---|---|---|---|
| fake | 程序内预设 plan/draft | 否 | 单元和故障注入 | 模型协议与真实行为 |
| replay | 冻结交互 fixture | 否 | 可重复演示和回归 | 当前供应商可用性 |
| live | DeepSeek API | 是 | smoke、兼容性、稳定性和成本 | 未覆盖场景的生产可靠性 |

## C4. 关键状态与证据术语

- `VERIFIED_RESULT`：模型草稿通过本地验证。
- `DEGRADED_SAFE_RESULT`：模型或证据路径失败，返回明确标记的确定性安全结果。
- `NEEDS_CLARIFICATION`：标题歧义，等待一次用户选择。
- `FAILED`：前置条件、状态或安全边界失败，不能发布正常结果。
- `STRONG/MODERATE/WEAK/INSUFFICIENT`：冻结规则下的证据强度，不是商品质量等级。
- `silver`：规则构造期望；`reviewed`：有人审过；`gold`：只有建立独立双审/仲裁流程后才能使用。

## C5. 指标怎样解释

- **Citation integrity 1.0：** 在冻结案例中，期望、工具和最终响应引用严格相等且能回库；不等于内容在现实世界绝对正确。
- **Structured validity 0.7：** 70% 案例得到有效结构化模型输出；其余包括故意触发失败并安全降级的场景。该指标不是单独放行条件。
- **Fallback rate 0.2：** 六个案例使用确定性降级；它描述路径分布，不是质量越高越好。
- **Verifier rejection 0.2：** 六个案例的草稿被本地验证器拒绝；证明拒绝路径被执行，不证明覆盖所有幻觉。
- **Workflow/clarification accuracy 1.0：** 仅针对 30 个 silver 冻结案例。
- **完整测试通过：** 测试数会随 P7 继续变化，因此不把某次数量当永久成果；面试前应在当前 commit 重跑完整 pytest、Ruff、依赖检查和阶段审计。

## C6. 自测答案

1. **为什么不是普通 RAG？** 项目不仅检索，还包含商品授权、三类业务工具、一次澄清、状态恢复、逐字段验证、预算和安全发布；检索只是其中一层。
2. **为什么没有向量库？** P5 没有独立证据证明复杂检索值得引入，且现有 silver benchmark 对词法有偏；先保留简单、可解释基线。
3. **模型有没有看到评论原文？** 生成阶段没有；模型结束后才在本地把已验证引用对应的原文附加给本地用户。
4. **为什么需要 verifier？** Structured Output 只证明格式，不能证明商品、引用、强度和排序被授权且正确。
5. **P6 为什么能够通过？** 先通过 30 案例离线 gate，再完成真实 DeepSeek 15 × 2 live gate；最后从私有明细重聚合并复核 P1–P4 lineage、源码和公开工件，完成审计返回 `READY_TO_CLOSE_P6`。
6. **P7 页面打开为什么还不能直接通过？** 页面可打开只证明服务启动。当前 API 异常、澄清恢复、公开泄漏、桌面/移动布局、三类 synthetic 任务、P6-backed 真实本地回归和工件身份都已验证；仍缺目标运营用户的结构化试用记录，因此阶段不能通过。

## D6. 技术面常问什么

### Q1：为什么用 LangGraph？

先说需求：标题歧义需要 interrupt/resume、进程重开和预算持久化；再说 LangGraph 只负责编排，确定性代码仍负责授权。不要回答“招聘要求所以用了”。

### Q2：Structured Output 为什么不够？

格式合法不等于商品已授权、引用存在、强度正确或工具可执行。还需要 resolver、workflow 前置条件、集合相等、SQLite citation verifier 和预算。

### Q3：如何防幻觉？

不承诺消灭幻觉。回答四层：调用前只发安全卡；生成后逐字段验证；引用三方相等并回库；失败时 repair 一次或确定性降级。

### Q4：为什么不用向量数据库？

P5 没有证明更复杂检索的收益；当前 benchmark 对词法有偏，下一步应先做人工 relevance 小集，再决定 embedding/reranker，而不是为关键词堆栈。

### Q5：怎样测试 Agent？

分层回答：契约/工具单测；图节点和 checkpoint 测试；CLI 入口测试；真实合成 SQLite + 编译图集成；本地 P4 store 的 30 案例离线评估；最后是真实 DeepSeek 30 次 live gate。

### Q6：如何控制 API 成本？

fake/replay 负责大多数回归；live 显式确认；SDK 自动重试关闭；每运行最多三次实际 HTTP attempt；记录 cache-hit/miss、output token 后按带日期的官方价格快照计算。

### Q7：公开产物如何防泄漏？

公开 schema 闭合；递归扫描 key 和 value；拒绝秘密、Authorization、商品/证据标识和 Windows/Unix/UNC 路径；只允许固定 lineage 字段/报告行携带哈希；双文件失败时不保留旧 PASS 或半对。

### “为什么 structured validity 只有 0.7？”

“30 个案例包含故意的恶意、无答案和 provider-failure 路径；部分输出应当被拒绝并安全降级。放行不是要求所有模型输出有效，而是要求每个正常/失败场景达到其期望状态、引用和安全门。”

“不能。它证明当前代码、配置和 15 个冻结 silver 案例在两次重复中的有界工程行为，不能覆盖模型升级、开放输入、并发负载或企业数据分布。生产可靠性还需要更长时间窗口、人工任务集、监控、故障演练和真实用户验证。”

### “Amazon 评论能公开吗？”

“数据可下载不等于可以按代码许可证再分发。原始数据、评论文本、用户/商品/证据标识和索引保持本地；公开仓库只放代码、合成 fixture、聚合指标和扫描后的报告。”
