# C2 分诊对照实验报告（2026-09-26）

## 一句话结论

**给工作台加一步"让模型参与排序"不划算：模型看着纯数字卡排出的顺序，与本地确定性规则几乎一模一样（tau 0.931），而对参考层的吻合度并没有实质提升（0.238 vs 0.186）。按事先定好的决策规则，C3（MCP 接入）不做。**

> 行话注：Kendall tau（肯德尔 τ）——量"两个排序有多一致"的数，+1 是完全同序，0 是没关系，-1 是完全反序。**什么时候用：**比较两份"先查谁后查谁"的清单时。

## 我们想知道什么

工作台的"问题分诊"靠本地规则排出核查顺序。两个悬而未决的问题：

1. 如果让大模型看着同样的数字自己排，它排得跟规则一样吗？（一样 → 模型没增量）
2. 模型排得比规则更接近"参考层"吗？（更接近 → 模型有增量）

> 行话注：**参考层**——用代标战役的 49,903 条模型盲标结果算出的每个商品每维度的"反对占比"，代表"词表判不了的那部分评论"里埋的信号。**它不是人工金标准**，只是独立的第二意见。

## 怎么测的

- 3 个受控商品 × 8 个维度；每个商品-维度跑一次真实的本地工作台诊断（确定性、无模型），拿支持/反对/冲突计数。
- 三种排序：
  1. **确定性规则**（本实验文档化的规则）：反对+冲突多的排前面，平手看匹配量；
  2. **参考层**：按代标算出的反对占比排，无参考数据的商品-维度直接剔除，不猜；
  3. **模型**：每次调用只喂一张纯数字卡（商品代号 + 六个计数，**无任何评论原文**），强制通过工具提交完整排序，温度 0，思考模式显式关闭。
- 三组 tau 两两对照；产出只进聚合工件（`artifacts/evals/triage-comparison-details.json` 本地、`artifacts/evaluation-summaries/triage-comparison.json`）。
- 安全红线全程遵守：API key 只在进程环境，不进命令行/磁盘/日志；`--live` 必须显式 `--acknowledge-live-api`。

## 结果（8/8 调用成功，2026-09-26 live）

| 维度 | 模型↔参考 | 规则↔参考 | 模型↔规则 |
|---|---|---|---|
| 容量与速度 | +0.33 | +0.33 | 1.00 |
| 清洁维护 | **+1.00** | +0.82 | 0.82 |
| 安装易用 | +1.00 | +1.00 | 1.00 |
| 制冰质量 | -1.00 | -1.00 | 1.00 |
| 漏水 | —（参考层全并列，tau 无定义） | — | 0.82 |
| 运行噪音 | +0.33 | +0.33 | 1.00 |
| 可靠性 | -1.00 | -1.00 | 1.00 |
| 尺寸便携 | **+1.00** | +0.82 | 0.82 |
| **聚合** | **+0.238** | **+0.186** | **+0.931** |

成本：8 次调用共 4,311 输入 + 828 输出 token，约 **0.0008 美元**。

## 三个发现

1. **模型看数字就能复现规则（tau 0.931）。** 每次调用的理由字段都逐字引用了卡片数字，没有编造。三个偏离里有两个（清洁维护、尺寸便携）其实是模型在平手破序时选得更好——对参考层 +1.00 vs 规则的 +0.82。
2. **但对参考层的提升是边际的（0.238 vs 0.186）。** 好两个维度、其余相同，聚合并不能证明"模型排序有增量"。
3. **制冰质量与可靠性双双 -1.00 是最重要的信号。** 模型和规则看的是同一组数字，得出同样排序，而这个排序与"盲区部分"的参考层完全反序。这把 C1 的结论推进一步：**与盲区的分歧来自数据本身（词表命中话题而非评价，E6），不是排序逻辑的问题——换谁来排都一样。**

## 决定：C3（MCP 接入）不做

事先定好的规则是"若模型排序 ≈ 确定性规则、或未显著胜过基线，则跳过 C3"。两条都命中：0.931 ≈ 1，0.238 vs 0.186 无实质差。给工作台加一步真实模型排序，等于增加成本、延迟、不确定性与新的故障面，换不来信息增量。**模型的正确位置仍是现在的"把数字卡讲成人话"，排序留在本地规则手里。**

## 局限（照实说）

- 双方都不是人工金标准：确定性侧来自"词表判得了"的评论，参考层来自"判不了"的盲区，两个集合不相交。
- 每维度只有 3 个商品，单个 tau 最多基于 3 对样本，只能看方向不能看精度。
- 每维度 1 次调用、温度 0，没有测采样方差。
- 确定性规则是本实验的文档化规则，不是工作台线上分诊的原序。

## 工程备忘

- DeepSeek API 对该模型**默认开思考模式且思考模式不支持强制 tool-call**（实测 400：`Thinking mode does not support this tool_choice`）。任何 tool-call 请求必须带 `extra_body={"thinking": {"type": "disabled"}}`——P6 网关早已如此，C2 复用了同一写法。这同时实证了"不开深度思考"的决定：合同钉死 `thinking: false` 本来就是唯一可行路径。
- 复用清单：`load_local_agent_resources`（店↔配置校验 + 3 受控商品）、`build_aspect_reference`（参考层）、`assert_public_workbench_safe`（出站安全扫描）、`DeepSeekModelGateway` 的请求形状。
